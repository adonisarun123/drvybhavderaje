# Internal linking and relationship structured data

Implements the Monk Mantra *Internal Linking and Structured Data Implementation Guide* (v1.0, 12 Nov 2026) on this site.

## How it works

| Piece | Where | Rule |
|---|---|---|
| In-copy links | `lib/links.tsx` → `TERM_LINKS`, `autolink()` | First mention of a topic links to its page; one link per target per page, three per paragraph, never the page itself. |
| Related Care grid | `lib/links.tsx` → `relatedServicesWithReason()` | Editor's picks (`related` on each page), parent hub, siblings of the same hub, a hub's children. No padding with pages that only share a group. Three to six links per page. |
| `relatedLink` | `lib/seo.ts` → `medicalWebPageJsonLd()` | Added to the existing WebPage node. Only paths the template renders as visible links; the page itself and duplicates are dropped. |
| `significantLink` | same | Not emitted. Pass `significantPaths` only when page-level click data supports it. |
| `isRelatedTo` / `isSimilarTo` | — | Not used. They belong on Service / Product entities; this site describes MedicalProcedure and MedicalCondition entities, and procedures are not marked as similar to one another. |
| Feature flag | `RELATIONSHIP_SCHEMA` | `"false"` removes `relatedLink` / `significantLink` only. Visible links stay. |
| Schema holdout test | `lib/link-experiment.ts`, `RELATIONSHIP_SCHEMA_HOLDOUT` | 21 holdout pages omit `relatedLink`; 23 test pages declare it. `"false"` ends the test. See Measurement. |
| Click measurement | `lib/analytics.ts` → `internal_link_click` | `link_type`: `related` (Related Care grid, child / sibling lists) or `contextual` (links in body copy). |
| Link map | `docs/internal-link-map.csv` | Generated by `npx tsx scripts/link-map.ts [base-url]` from the rendered pages: every internal link, its placement, whether it is declared as `relatedLink`, and whether the destination answers 200. Header and footer links are listed once as "Every page". The script exits with an error if a declared link is not visible or a destination is not 200. Re-run after any content or link change. |

## Changing a related link

Edit the page's `related` list in `lib/content.ts` or `lib/procedures.ts` (or `seeAlso` in `lib/sub-procedures.ts`), then re-run the link map script. The grid and the structured data both follow. Clinical relationships need the doctor's confirmation. The six editor's picks queried at the 12 Nov 2026 audit (Ear Reconstruction → Craniosynostosis, Chin Augmentation → Liposuction, Liposuction → Facelift, Head and Neck Cancer → Breast hub, Facial Injuries → Hand, Face hub → Jaw Surgery) were confirmed by Dr Deraje on 12 Nov 2026 (relayed by Arun); none are open.

## QA

- `npm test` — unit tests for the link rules and the structured-data flag.
- `E2E_BASE_URL=<site> npx playwright test internal-links` — every declared `relatedLink` is a visible link on the page (read-only).
- After deploy: Schema Markup Validator and Search Console URL Inspection on one page per template.

## Measurement

Two separate questions, measured separately.

**1. Do the visible links help visitors?** GA4 `internal_link_click` by `link_type` and `page_path`, alongside `generate_lead`, `whatsapp_click` and `phone_click`. Review monthly in the SEO report.

**2. Does the `relatedLink` markup itself change anything?** A holdout test, `relatedlink-holdout-2026-11`.

- **Groups.** The 44 pages that declare `relatedLink` from their own content were split within each page type by a hash of the path (nobody chose). Home and the procedures index are outside the test. The exact pages are in `lib/link-experiment.ts` and in the "Schema test group" column of the link map.

| Page type | Test (markup on) | Holdout (markup off) |
|---|---:|---:|
| Featured craniofacial | 2 | 2 |
| Featured cosmetic | 5 | 5 |
| Other services | 5 | 4 |
| Sub-procedure pages | 8 | 7 |
| Craniosynostosis type pages | 3 | 3 |

- **What differs.** Only the `relatedLink` property. Both groups have the same visible links, titles and content rules.
- **Baseline.** The 28 days before the release that contains this test. Before that release every page declared `relatedLink`, so this is a removal test: it measures what the holdout pages lose, if anything.
- **Start.** The day the commit adding `lib/link-experiment.ts` is deployed to production. Record that date in the SEO execution tracker.
- **Run.** At least 8 weeks, 12 if volume stays low. Do not edit the group lists during the run.
- **Read-out.** Search Console, page-level clicks, impressions and average position for the pages of each group. Compare each group's change from its own baseline with the other group's change (difference in differences), not the raw totals: the groups start from different traffic levels.
- **Log during the run.** Every content edit, title change, new backlink and site release that touches a page in either group, with its date. A page that gets its own large change is dropped from the comparison.
- **Limits.** At the November 2026 baseline the whole site earned about 160 clicks in 20 days, so a small effect will not be distinguishable from noise; an inconclusive result is the likely outcome and is still a result. The same release also removed padding links from the Related Care grids on every page, in both groups, so that change cannot be separated from the calendar. `relatedLink` is not a property Google documents as used for ranking or rich results.
- **Ending the test.** Set `RELATIONSHIP_SCHEMA_HOLDOUT="false"` in Vercel (no code change), or empty the holdout list. Unless the holdout pages do measurably better without it, restore the markup everywhere: it is an accurate description of the page.
